# systems-hub

面白いシステムを個人で設計・開発するために、テーマ、設計上の問い、比較、判断理由を残す場所。
一つのプロジェクトを始めるためだけでなく、今後もテーマを考える恒久的な入口として使う。

## テーマ選びの考え方

- 仕組みの解明と設計・実装の面白さを重視する。コンテナ、CI/CD、プラットフォームへの関心を出発点に、未知の技術も探索する。
- AIありきでテーマを選ばない。作りたいシステムに有効なら、AIを中核に据えることも含めて考える。
- 業務への直接的な有用性は必須にしない。既存製品と重なる場合も、自分なりの設計、着眼点、簡潔さを探る。
- 長期的に育てられる構想と、短期間で動かして確かめられる成果を両立する。
- 本体の設計から疑問が生まれ、必要な実験を行い、その結果を設計に戻す流れを基本とする。

## リポジトリの使い分け

| 場所 | 役割 |
| --- | --- |
| `systems-hub` | テーマ候補、動機、既存システムとの比較、設計上の問い、採用・保留・不採用の理由 |
| 本体プロジェクトのリポジトリ | PoCと継続開発のコード、実行方法、具体的な設計、検証結果 |
| `skill-lab`などのLab | 必要に応じた独立実験、prototype、benchmark、障害シミュレーション。設計判断を支える実験場 |
| `ai-thinking-lab` | AI固有の実験を扱う既存の場所。当初の構想ではPrivate化・積極利用しない想定で、現在の設定状態は本リポジトリでは確認しない |

テーマと最初に確かめる範囲を具体化し、実装開始時に本体リポジトリを作る。本体へ育てるPoCはそこで始め、Labを必ず経由する必要はない。

本体へ具体的な設計を移す場合は、ここには選定理由と参照先を残す。同じ設計を両方で更新する二重管理は避ける。Labの改名や既存リポジトリの設定変更は別途判断する。
